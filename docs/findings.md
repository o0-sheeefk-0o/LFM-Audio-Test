# 評価のまとめ: LFM2.5-Audio-1.5B-JP に会話とツール実行を任せられるか

[LiquidAI/LFM2.5-Audio-1.5B-JP](https://huggingface.co/LiquidAI/LFM2.5-Audio-1.5B-JP) を音声エージェント（音声で会話し、必要に応じてツールを呼ぶ）として使えるかを検証した結果のまとめ。個々の計測値と手順は [README](../README.md) の「検証結果」と [performance.md](performance.md) にある。

## 結論

**単体で、会話の継続とツール実行の両方を任せるのは荷が重い。** 速度は十分に出る（Apple M3 でリアルタイムの約 2 倍）。答えのはっきりした単発の質問や、言い方のはっきりした単純なツール呼び出しはこなせる。一方で、次の 4 点はモデル自体の限界で、前処理やプロンプトの工夫では直らなかった。

1. 会話履歴があると、自由回答の依頼に**直前の返答をそのまま返す**
2. ツールを**呼ぶかどうかの判断**が、呼ばなくてよい質問と分けきれない
3. 数や固有名詞の聞き取りが不正確で、**ツールの選択と引数**を誤る
4. **長いシステムプロンプト**（1k tokens 程度から）で指示や資料を参照できなくなる

用途を「決まった音声コマンド＋短い雑談」に絞るなら実用の余地はある。会話とツールの質が必要なら、文字起こし＋テキスト LLM と組み合わせる構成を勧める（後述。この構成自体は未検証）。

## 検証の条件と範囲

- 期間: 2026-10-24〜25
- 環境: MacBook Air（Apple M3、16GB）、PyTorch MPS、bf16（一部 int8 量子化）、liquid-audio 1.3.0
- 入力音声: 大半は macOS の `say -v Kyoko` で合成した音声。一部はブラウザのマイクから WebRTC 経由で入れた実録音
- 規模: ツール判定は約 30 問、会話は数本。マシンは 1 台のみ。傾向をつかむための検証で、統計的に十分な規模ではない

## できたこと

| 項目 | 結果 |
|---|---|
| 速度 | 最初のトークンまで 0.1〜0.15 秒、生成はリアルタイムの約 2 倍（RTF 約 0.5）。高速化前は RTF 1.2〜2.6 で、再生が途切れていた |
| 単発の質問 | 「日本で一番高い山は？」のような答えのはっきりした質問は、履歴があっても正しく答える |
| 単純なツール呼び出し | 「大阪の天気はどう？」「3分のタイマーをセットして」「渋谷でラーメン屋を探して」は、正しいツールを呼んで結果を音声で答えた。ただし後述の 2 段階方式の工夫が前提 |
| ツール結果を使った応答 | 結果を渡せば、それを読み上げる形で崩れずに答える |

## 難しかったこと

### 1. 前の返答を繰り返す

会話履歴があると、自由回答の依頼に直前の返答をそのまま返すことが多い。

| 会話 | 結果 |
|---|---|
| 「自己紹介して」→「何か面白い話をして」→「なぞなぞを出して」→「答えは？」 | 2 ターン目以降すべて、自己紹介がそのまま返る |
| 「東京の天気を教えて」（ツール）→「何か面白い話をして」 | 天気の答えがそのまま返る |
| 「日本で一番高い山は？」→「何か面白い話をして」 | 富士山の話を続ける（作り話を含む） |

- 同じ質問を会話の最初に聞くと、正しく答える（物語を話す、なぞなぞを出す）
- ノイズのない合成音声で、高速化をすべて切っても再現する
- system プロンプトの有無、text temperature（0 / 0.7）、ツール結果の渡し方（4 通り）を変えても直らない。過去の返答をテキストだけにすると悪化した
- 履歴を入れなければ繰り返さない。ただし「答えは？」「二番目に高い山は？」のような、前の発話を受けた質問に答えられなくなる

対策として、返答の書き出しが過去の返答と同じなら打ち切り、履歴なしで答え直す処理を入れた。繰り返し自体は防げるが、答え直しても自己紹介になることが多く、効果は限定的だった。

### 2. 自由回答が不安定

自由回答の依頼では、自己紹介が「迷ったときの答え」になっている。合成音声の「何か面白い話をして」は、そのままなら物語を話すが、**前後に 0.8 秒の無音を足すだけで自己紹介になる**。WebRTC 経由の録音でも自己紹介になった（無音を削っても、16kHz に変換しても同じ）。一方、「明日の天気教えて」のような依頼は、どの条件でも同じ答えになった。

### 3. ツール実行

**公式テンプレート通りの使い方（ネイティブ方式）では実用にならない。** system にツール一覧と既定の指示（`Respond with interleaved text and audio.`）を入れるとツールを呼ばず、「天気は提供できません」と断ったり、時刻を捏造したりする。既定の指示を外すとツールコールは出るが、応答文が崩れる。

そこで、ツールを呼ぶかの判定を別のパスに分け（判定パスは既定の指示なし・今回の発話だけ）、先頭トークンが `<|tool_call_start|>` になる確率をしきい値で判定する方式（2 段階方式）を作った。単純な依頼はこれで呼べるようになったが、次の問題が残る。

| 問題 | 例 |
|---|---|
| 呼ばなくてよい質問で呼ぶ | 15 問中 6 問で呼んだ。「日本の首都は？」「もう一回言って」「こんにちは」「おはよう」で `get_current_time`、「二番目に高い山は？」で `get_weather(city='Mount Everest')` |
| 判定の確率が分けきれない | 呼ぶべき質問は p=0.006〜0.78、呼ばなくてよい質問でも最大 0.12。しきい値をどこに置いても誤る |
| ツールの選択を誤る | 「1たす1は？」が `set_timer(label='1+1', minutes=1)`。実録音の「明日の天気教えて」が `get_current_time`（ツールの説明に「いつ使うか」を書くと直った） |
| 引数を誤る | 「123かける456」が `123456 * 0.96`、「札幌」が `Tokyo`、「2980円」が `1980` |
| 前の発話を受けた依頼に弱い | 判定パスに履歴を入れると 2 ターン目以降ほぼ呼ばなくなるため、今回の発話だけで判定している。そのため「じゃあ大阪は？」は正しく呼べない |

ツールの説明文を改善すると、27 問中の正解は 22 → 23 問になった。数の聞き取りや判定の誤りは、説明文では直らなかった。

### 4. 長いシステムプロンプト

社員名簿を system に入れて、その中身を質問した。

| system の長さ | 結果 |
|---|---|
| 約 1k tokens | テキストで質問すると 3 問中 1 問正解。音声で質問すると部署のみ当たる程度 |
| 約 2k tokens | ほぼ誤答。崩れも出始める |
| 約 4k tokens | 誤答。崩れが目立つ |
| 約 8k tokens 以上 | 文章が崩れる |

同じ入力を CPU fp32 で実行しても生成テキストが完全一致したので、MPS の計算誤差ではなくモデルの限界。既定の指示（`Respond with interleaved text and audio.`）は外せない（外すと中国語が混ざるなどして崩れる）。

## モデルの限界と見誤りやすかったこと

「何を聞いても同じ返答が返る」という症状には、モデル以外の原因も重なっていた。どちらもアプリ側（fastrtc の既定の音声処理）の問題で、修正済み。同じ構成で検証する場合は注意が必要。

| 原因 | 何が起きていたか | 対策 |
|---|---|---|
| 発話の切り出し | fastrtc の既定（`ReplyOnPause`）は言い始めを捨て、言葉の途中の 0.5 秒程度の間で発話終了とみなす。質問の冒頭 0.6〜1.2 秒しかモデルに届かず、直前と同じ返答が返っていた | 話し始め前の音声も残し、無音が 0.8 秒続くまで終了とみなさない（`vad.py`） |
| 応答音声の残響 | 応答の生成は再生より速く終わるため、ブラウザでまだ再生中の応答音声の残響や物音（-40〜-50 dBFS）を次の質問として拾っていた。実際の会話の録音 8 件中 3 件がこれで、意味のない入力にツール判定が反応し、時刻の答えが繰り返されていた | 再生が終わるまでマイク入力を捨て、-35 dBFS 未満の音は無視する（`vad.py`） |

モデルが実際に受け取った音声を録音して聞き直せるようにしておくと、原因の切り分けが速い（このリポジトリの画面では会話ログで再生できる）。

## 使うなら（構成の提案。いずれも未検証）

1. **用途を絞る**: 天気・タイマーのような決まった音声コマンドと短い雑談に限る。system プロンプトは短く保ち、会話は数ターンでリセットする
2. **カスケード型**: このモデル（または別の音声認識）で文字起こしし、ツール呼び出しに強いテキスト LLM に会話とツール判断を任せ、音声合成で返す。会話とツールの質は上がるが、応答開始は LLM と音声合成のぶん遅くなる
3. **ハイブリッド**: 雑談の音声応答はこのモデルに任せて速さを活かし、ツール判定と引数の取り出しだけを文字起こし＋テキスト LLM に置き換える。このリポジトリの 2 段階方式の判定パスを差し替える形になる。前の返答を繰り返す癖は残る
