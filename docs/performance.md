# 推論速度の計測と高速化

LFM2.5-Audio-1.5B-JP の speech-to-speech を Apple M3 の MacBook Air で動かしたときの、ボトルネックの分析と高速化の記録。

## 結論

| 指標（画面を WebRTC 経由で操作して計測） | 高速化前 | 高速化後 |
|---|---:|---:|
| 生成速度 | 6.3〜14 step/s | **31.5〜32.2 step/s** |
| RTF（生成時間 ÷ 音声の長さ。1 未満ならリアルタイムより速い） | 1.18〜2.59 | **0.50〜0.57** |
| 応答の最初のトークンまで | 0.32〜5.15 秒 | **0.10〜0.14 秒** |
| ツール判定パス | 1.0〜16.7 秒 | **0.16〜0.73 秒** |
| 長い system（約 8k トークン）での 2 ターン目以降の最初の音声まで | 17〜21 秒 | **0.5〜1.3 秒** |
| GPU メモリ（MPS ドライバーの確保量） | 8.4〜10.1 GB | **2.3 GB** |

高速化前は生成がリアルタイムより遅く、再生が途切れる状態だった。高速化後は RTF が約 0.5 になり、リアルタイムの約 2 倍の速さで生成できる。

最も効いたのは次の 3 つ。

1. 音声フレーム生成部（depthformer）の書き直しと `torch.compile`
2. int8 重み量子化
3. ターンをまたいだ KV キャッシュの使い回し（prefix キャッシュ）

TensorRT は macOS では使えないため対象外とした（[後述](#検討したが採用しなかったもの)）。

## 計測環境と方法

| 項目 | 値 |
|---|---|
| マシン | MacBook Air 13 インチ M3（`Mac15,12`）、メモリ 16GB、**ファンなし** |
| OS | macOS 27.0.1 |
| 実行 | PyTorch 2.14.1（MPS バックエンド）、transformers 5.20.2、liquid-audio 1.3.0、bf16 |
| 入力 | `bench/fixtures/*.wav`（macOS の `say -v Kyoko` で合成した固定の質問音声） |
| 計測スクリプト | `bench/bench_speed.py`、集計は `bench/summarize.py`、結果は `bench/results/*.json` |

`bench_speed.py` には 4 つのモードがある。

| モード | 測るもの |
|---|---|
| `components` | 1 ステップの部品ごとの時間 |
| `e2e` | 1 ターン全体（3 ケース × 3 回の中央値）。起動直後の 1 ターン目は別に記録 |
| `prefill` | system の長さと prefill 時間の関係 |
| `multiturn` | 長い system と 3 ターンの会話での遅延 |

部品ごとの計測では、次の 3 つの時間を取る。

- **latency_ms**: 1 回ごとに GPU と同期して測った時間
- **cpu_ms**: Python から GPU にカーネルを積み終わるまでの時間
- **pipelined_ms**: 同期せずに連続実行したときの 1 回あたりの時間

`cpu_ms` が `pipelined_ms` に近ければ CPU（Python とカーネル起動）が律速、十分小さければ GPU が律速と判断する。

### 計測の注意点

- **発熱による性能低下**: ファンのない MacBook Air では、重い処理が続くと最大で約 1.8 倍遅くなる。8k トークンの prefill を新しいプロセスで交互に測った結果は次のとおり。int8 と bf16 は冷えた状態ではほぼ同じだが、続けて回すと両方とも遅くなる。`bench/results/*-prefill.json` の 8k の値（13〜16 秒）はこの影響を受けている

| 実行順 | 4 回の prefill 時間（秒） |
|---|---|
| 1. bf16 | 6.97, 6.76, 6.87, 7.12 |
| 2. int8 | 7.05, 7.37, 7.63, 7.85 |
| 3. int8 | 8.37, 9.21, 10.89, 12.50 |
| 4. bf16 | 11.34, 10.83, 10.39, 10.05 |

- **メモリの逼迫**: 計測中、マシン全体のメモリ使用率は 87％、スワップは 9〜12GB 使われていた（他のアプリを含む）。ばらつきの一因になっている
- **初めての形状**: MPS は入力形状ごとにカーネルを初回生成する。新しい長さで初めて prefill するときは、数秒〜十数秒余計にかかることがある

## アーキテクチャと律速の分析

### 生成の流れ

```
[prefill]  system + 会話履歴 + ユーザー音声（conformer でエンコード）を LFM2 バックボーンに一括入力
[decode]   以下を 1 ステップずつ繰り返す（interleaved 生成）
  テキスト 6 ステップ: バックボーン 1 トークン → テキストヘッド（語彙 65,536）→ 次のテキストトークン
  音声 9 ステップ:     バックボーン 1 トークン → depthformer（6 層 × 8 コードブックを逐次）→ 音声コード 8 個
                       → Mimi デコーダで 80ms ぶんの波形にする
```

音声 1 フレームは 80ms。9 フレーム（720ms）の音声に 15 ステップかかるので、リアルタイムで再生し続けるには **20.8 step/s 以上**が必要。

### 高速化前の内訳（`baseline-components.json`）

| 部品 | 時間 | CPU 側 | 判定 |
|---|---:|---:|---|
| バックボーン 1 ステップ | 28.1 ms | 3.9 ms | GPU 律速 |
| テキストヘッド | 3.2 ms | 0.0 ms | GPU 律速 |
| 音声フレーム生成（depthformer、8 コードブック） | 31.6 ms | 13.4 ms | GPU 律速（カーネル数過多） |
| Mimi デコード 1 フレーム | 11.6 ms | 4.2 ms | GPU 律速 |
| **テキスト 1 ステップ / 音声 1 ステップ** | **31.3 / 71.5 ms** | | 見積もり RTF 1.15 |

音声 1 ステップの内訳は、バックボーン 39％、depthformer 44％、Mimi 16％。

M3 のメモリ帯域は約 100GB/s。この値から、重みの読み出し量で決まる下限を見積もった。

| 部品 | 重みの読み出し量 | 下限（bf16） | 実測 |
|---|---|---:|---:|
| バックボーン | 約 2.1GB / ステップ（埋め込みを除く） | 約 21 ms | 28.1 ms（帯域の約 8 割を使用） |
| depthformer | 134MB × 8 回 / フレーム | 約 11 ms | 31.6 ms |

- バックボーンはほぼ帯域律速なので、速くするには重みを小さくする（量子化）しかない
- depthformer は下限の約 3 倍かかっている。1 フレームあたり 8 コードブック × 6 層 × 数十個の小さなカーネルを起動しており、その固定コストが支配的

### ① depthformer の書き直しと torch.compile（`fast_depthformer`）

元の `LFM2AudioModel._sample_audio_frame` が遅い理由は次のとおり。

- RoPE を複素数演算でやっている
- KV キャッシュを `torch.cat` で伸ばしている
- サンプリングが topk → masked_fill → softmax → multinomial
- これらを 8 コードブック × 6 層ぶん、小さなカーネルのまま回している

`accel.FastDepthformer` で次のように書き直し、1 フレームぶんを 1 つのグラフとして `torch.compile`（inductor の Metal バックエンド）した。

- 位置は常に 0〜7 なので、RoPE の cos/sin を事前計算して実数演算にした
- 8 コードブックのループを展開して、形状を静的にした
- top-k サンプリングを Gumbel-max（topk した値に Gumbel ノイズを足して argmax）にした。分布は元と同じ
- temperature をテンソルで渡し、値を変えても再コンパイルしないようにした

途中経過は次のとおり。

| 版 | 1 フレーム | CPU 側 |
|---|---:|---:|
| 元の実装 | 31.6 ms | 12.6 ms |
| 書き直し（コンパイルなし） | 45.6 ms | 25.1 ms |
| 書き直し＋torch.compile | 19.3 ms | 4.2 ms |
| ＋注意機構を要素積と和で書いて融合、GLU の w1/w3 を連結 | **15.0 ms** | 1.6 ms |

途中で見つけた不具合: temperature のテンソルを毎フレーム `torch.tensor(..., device="mps")` で作っていた。CPU から MPS への転送は、それまでに積んだ GPU 処理の完了待ち（同期）になる。このため、int8 版では 1 フレームの CPU 時間が 16.3ms まで膨らんでいた。値ごとにテンソルを使い回すように直し、16.3ms → 5.1ms（実時間 13.9ms）になった。

正しさの確認: 実際の会話の隠れ状態 16 個（128 コードブック分）で、元の実装と greedy の出力を比べた。

| 比較対象 | 一致数 |
|---|---:|
| 書き直し版（コンパイルなし） | 128/128 |
| torch.compile 版 | 127/128（bf16 の演算順の違いによる僅差の入れ替わりのみ） |

temperature 1.0、top-k 4 で 400 回サンプリングした分布も元の実装と同程度だった。

コンパイルには 1 パターンあたり約 20 秒かかる。起動時のウォームアップで済ませ、2 回目以降は inductor のディスクキャッシュで数秒になる。

### ② Mimi デコードを CPU スレッドへ（`mimi_on_cpu`）

Mimi デコードは CPU（2 スレッド）でも MPS と同程度の速さだった。

| 場所 | 1 フレームずつ | 3 フレームまとめて |
|---|---:|---:|
| CPU | 10.9 ms/フレーム | 4.6 ms/フレーム |
| MPS | 11.0 ms/フレーム | 4.5 ms/フレーム |

`accel.MimiWorker` で CPU の別スレッドに移し、GPU での生成と並列に動かした。たまったフレームはまとめてデコードする。GPU の律速経路から 1 フレームあたり約 12ms が外れた。

### ③ int8 重み量子化（`int8`）

バックボーンと depthformer はメモリ帯域律速なので、Linear の重みを出力チャネルごとのスケール付き int8 にした（`accel.Int8Linear`）。行列積は `torch._weight_int8pack_mm` を使う。テキストヘッドも、埋め込み行列の int8 複製で計算する。

`_weight_int8pack_mm` は入出力の次元が 32 の倍数でないと使えない。このため depthformer の出力層（語彙 2049、約 200 万パラメータ）だけ bf16 のまま残した。

MPS での行列積の速さ（1 行入力、12288×2048）:

| 方式 | 時間 |
|---|---:|
| bf16 | 0.548 ms（92GB/s） |
| int8 | 0.278 ms |

int8 の相対誤差は約 1％。多数行の入力（prefill）でも bf16 と同等の速さ（8106 行で 3〜10％遅い程度）だった。

途中で見つけた不具合: 最初は「入力が多数行なら bf16 に戻してから計算」という分岐にしていた。ところが bf16 に戻す処理だけで 1 回 5.5ms かかり、応答の最初のトークンまでの時間が 0.16 → 0.37 秒に悪化した。常に int8 の行列積を使うように直した。

| 部品 | ② | ③ |
|---|---:|---:|
| バックボーン | 27.7 ms | 15.7〜17.3 ms |
| テキストヘッド | 3.3 ms | 1.8 ms |
| 音声フレーム | 16.2 ms | 10.1〜10.7 ms |

品質の確認:

- depthformer の greedy 出力は、元の bf16 実装と 123/128 一致した
- 3 つの質問の応答音声を同じモデルの ASR で文字起こしすると、表示テキストと一致した（例: 「東京の今日の天気は、曇りで気温は10度、湿度は61%です。」）

### ④ prefix キャッシュ（`prefix_cache`）

高速化前は、生成のたびに次をやり直していた。

- system プロンプトと会話履歴全体の prefill
- 過去の音声の conformer エンコード

④ では、生成後の KV キャッシュ（LFM2 の conv 状態を含む）をセッションに保存し、次のパスでは増えた部分だけを処理する。ツール判定パスの system（ツール一覧を含め約 450 トークン）も 1 回だけ処理し、毎ターン複製（約 0.6ms）して使う。

前半を prefill したキャッシュに後半を足した結果は、全体を一括で prefill した結果とコサイン類似度 0.99986 で一致した。差は bf16 の演算順の違い程度。

system の長さ × 3 ターンの会話での「最初の音声まで」（`multiturn`）:

| system の長さ | ターン | ③ キャッシュなし | ④ キャッシュあり | ⑤ ＋メモリ削減 |
|---|---:|---:|---:|---:|
| 短い（約 40 トークン） | 1 | 1.40 秒 | 1.71 秒 | 1.09 秒 |
| | 2 | 1.21 秒 | 0.39 秒 | 0.38 秒 |
| | 3 | 1.04 秒 | 0.56 秒 | 0.38 秒 |
| 約 2k トークン | 1 | 5.03 秒 | 6.53 秒 | 4.28 秒 |
| | 2 | 5.08 秒 | 0.77 秒 | 0.42 秒 |
| | 3 | 5.12 秒 | 0.58 秒 | 1.04 秒 |
| 約 8k トークン | 1 | 17.72 秒 | 20.89 秒 | 22.69 秒 |
| | 2 | 17.12 秒 | 0.55 秒 | 1.28 秒 |
| | 3 | 21.28 秒 | 0.50 秒 | 0.81 秒 |

- 2 ターン目以降は、system の長さにほぼ関係なく 1 秒前後になった
- 1 ターン目は system 全体の prefill が必要なので速くならない（prefill は約 0.85ms/トークンの演算律速）
- 応答テキストはキャッシュなしの場合とほぼ同じだった。キャッシュなしと比べると、9 ターン中 7 ターンが同一で、残りは bf16 の誤差による言い回しの違い

### ⑤ メモリ削減（読み込み方法の変更）

モデルを MPS 上で読み込むと、読み込み時の一時領域と量子化前の bf16 重みが MPS のメモリプールに残る。実際に使っている量よりはるかに大きな領域を確保し続けていた。CPU 上で読み込み、量子化してから GPU に移すように変えた。

| 構成 | 実使用 | ドライバー確保量（変更前 → 変更後） |
|---|---:|---:|
| 最適化なし | 3.4 GB | 8.49 → **4.51 GB** |
| 全部入り | 1.9 GB | 10.05 → **2.25 GB** |

16GB 機ではスワップを減らす効果がある。速度は誤差の範囲で同等か、やや改善した。

### 起動時のウォームアップ

`Engine.warmup()` で短い生成とツール判定を 1 回ずつ走らせ、`torch.compile` と MPS カーネルの初回生成を起動時に済ませる。

| 状態 | ウォームアップ時間 |
|---|---:|
| 初回（コンパイルあり） | 約 25 秒 |
| 2 回目以降（コンパイル結果をキャッシュ済み） | 約 4 秒 |

起動直後の 1 ターン目で最初の音声が出るまでは 1.43 → 1.10 秒になった。

## 検討したが採用しなかったもの

- **TensorRT**: NVIDIA の公式サポート表で、対応 OS は Linux / Windows / Jetson 等に限られる。macOS と Apple Silicon は対象外で、GPU も NVIDIA の SM 7.5 以上が前提（[Support Matrix](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html)）。このマシンでは使えない
  - NVIDIA 環境に移す場合でも、TensorRT-LLM の対応モデル一覧（`docs/source/models/supported-models.md`）に LFM2（`Lfm2ForCausalLM`）はない。バックボーンは自前でモデル実装を書く必要がある
  - 形状が固定の部品（conformer、depthformer の 1 フレーム、Mimi デコーダ）なら ONNX 経由で TensorRT 化できる可能性がある
  - CUDA 環境ではまず `torch.compile` の CUDA Graphs（`mode="reduce-overhead"`）を試すのが手軽
- **prefill だけ bf16 に戻す**: 上記のとおり、bf16 に戻す処理が重く逆効果だった。int8 の行列積は多数行でも bf16 と同等の速さ
- **Mimi を 3 フレームまとめて MPS でデコード**: 1 フレームあたりは速くなるが、最初の音声が 160ms 遅れる。CPU スレッドで並列に動かすほうが律速経路から完全に外せるので採用しなかった

## 残っているボトルネックと次の候補

| 項目 | 現状 | 候補 |
|---|---|---|
| 長い system での 1 ターン目 | prefill は演算律速（約 0.85ms/トークン。8k で約 7 秒、発熱時は 10 秒超） | system プロンプトを変えた時点で裏で prefill しておく |
| バックボーン 1 ステップ | int8 で 15.7ms（帯域の下限は約 11ms）、CPU 側 2.6ms | LFM2 の decode を自前で薄く書いて torch.compile する、int4 量子化 |
| 毎ステップの GPU 同期 | トークンの値で分岐するので毎ステップ同期している | 次のバックボーン計算を先に積んでから前のトークンを確認する（1 ステップ遅れの判定） |
| 発熱 | 長時間の生成で最大約 1.8 倍遅くなる | RTF 約 0.5 の余裕があるので、通常の会話では途切れない見込み |
| 実行系そのもの | PyTorch MPS | Liquid 公式の GGUF 版（llama.cpp、Metal）。macOS arm64 のビルド済みランナー付き。上限の目安として比較する価値がある |

## 再現手順

```bash
# 段階ごとの計測（--opts で有効にする最適化を指定）
uv run python bench/bench_speed.py components --opts none --label baseline
uv run python bench/bench_speed.py e2e --opts fast_depthformer --label opt1-depthformer
uv run python bench/bench_speed.py e2e --opts fast_depthformer,mimi_on_cpu --label opt2-mimi-cpu
uv run python bench/bench_speed.py e2e --opts fast_depthformer,mimi_on_cpu,int8 --label opt3-int8
uv run python bench/bench_speed.py multiturn --opts all --label opt5-memory

# 表にまとめる
uv run python bench/summarize.py baseline opt1-depthformer opt2-mimi-cpu opt3-int8 opt4-prefix-cache opt5-memory

# int8 と bf16 の prefill 比較（発熱の影響を見るため、新しいプロセスで交互に実行する）
for m in none int8 int8 none; do uv run python bench/prefill_int8_vs_bf16.py $m; done
```

`bench/results/baseline-*.json` は、`accel.py` を入れる前のコードで計測したもの。
