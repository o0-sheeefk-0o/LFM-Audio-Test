# LFM2.5-Audio-1.5B-JP speech-to-speech 検証

[LiquidAI/LFM2.5-Audio-1.5B-JP](https://huggingface.co/LiquidAI/LFM2.5-Audio-1.5B-JP) の付属 Gradio デモ（`liquid_audio.demo.chat`）を拡張し、次のことを検証できるようにしたもの。

- **システムプロンプト**: 画面から自由に入力できる。トークン数、コンテキスト使用量、最初のトークンが出るまでの時間を表示する
- **ツールコール**: サンプルツール 5 個（天気・時刻・計算・レストラン検索・タイマー）を渡し、モデルがツールを呼んだら実行して結果を返し、音声で答えさせる

付属デモからの主な変更点:

- CUDA 固定だったところを CUDA → MPS (Apple Silicon) → CPU の自動選択にした（`LFM_DEVICE=cpu` などで上書き可）
- 2 ターン目以降に system ターンが重複して入るバグを修正した（`len(chat.text) == 1` が常に真になっていた）
- 推論を高速化した（RTF 1.1〜1.3 → 約 0.5。詳細は [docs/performance.md](docs/performance.md)）

## セットアップと起動

```bash
uv sync
uv run python app.py   # → http://localhost:7860
```

モデルの重み（約 3.7GB）は初回起動時に Hugging Face キャッシュへダウンロードされる。

## 画面の使い方

| 項目 | 内容 |
|---|---|
| システムプロンプト | 自由に入力できる。**次の発話時**に反映され、前回から変わっていれば会話履歴を自動でリセットする |
| モデル既定の指示 | モデルカード推奨の `Respond with interleaved text and audio.` を先頭／末尾に付けるか、付けないかを選ぶ |
| ダミー資料を追記 | 指定トークン数ぶんの社員名簿を追記する。「木村さくらさんの部署と内線番号は？」のように聞けば、長文の奥にある情報を参照できるかを確認できる |
| ツールの扱い方 | 2 段階（既定）／ネイティブ。詳しくは下記 |
| ツール判定しきい値 | 2 段階方式で使う。各ターンで判定に使った確率は統計表の「備考」に出る |
| ツール定義 | JSON で編集できる。実装のないツール名を足した場合はモック応答（`{"status": "ok", ...}`）を返す |
| 音声入力（発話の切り出し） | 話し終わりと判定する無音の長さ（既定 0.8 秒）、VAD のしきい値（既定 0.5）、発話とみなす最小音量（既定 -35 dBFS）。質問が途中で切れるときは無音の長さを伸ばし、マイクの音量が小さくて反応しないときはしきい値と最小音量を下げる |
| 前の返答の繰り返し対策 | 「生成パラメータ」内。返答の書き出しが前の返答と同じなら、履歴を使わずに答え直す（既定オン）。詳しくは下記「前の返答の繰り返し」 |
| 実際にモデルへ渡す system ターン | ツール定義を含めた最終的な system ターン（公式の `chat_template.jinja` と同じ書式） |

会話ログには、ツールの呼び出し内容とモデルに返した結果が折りたたみで表示される。モデルが受け取ったユーザーの音声も再生できる（`outputs/recordings/` に保存。起動のたびに空にする）。

### 発話の切り出しについて

fastrtc の既定の切り出し（`ReplyOnPause`）は 0.6 秒ごとの区切りで判定する。次の 2 つの理由で、質問の冒頭（0.6〜1.2 秒）しかモデルに届かないことがあった。

- 話し始めを検出した区切りより前を捨てる（言い始めが欠ける）
- 発話が 0.1 秒未満の区切りが 1 つ来た時点で発話終了とみなす（言葉の途中の間で切れる）

冒頭だけが届くと、モデルは**何を聞いても直前と同じ返答（例: 自己紹介）を繰り返す**。ただし、質問を最後まで渡しても、自由回答の依頼では同じことが起きる（下の「前の返答の繰り返し」を参照）。

もう 1 つ、応答音声の残響を発話として拾う問題もあった。応答の生成は再生より速く終わる（RTF 約 0.5）。fastrtc は生成が終わった時点でマイク入力の受け付けを再開するが、ブラウザではまだ応答音声が数秒再生されている。その声の残響や物音（-40〜-50 dBFS）を次の発話として拾っていた。意味のない入力にもツール判定が反応して時刻ツールを呼び、「東京時間で15時40分です」が何度も返っていた。実際の会話の録音 8 件のうち 3 件がこれだった（普通の声は -16〜-21 dBFS）。

`vad.py` では次のように変えている。

- 0.4 秒ごとに直近 1.2 秒の窓で VAD をかける
- 話し始める前の 0.8 秒も残す
- 無音が 0.8 秒続いたら発話終了とする
- 応答音声の再生が終わる見込みの時刻（出力した音声の長さから見積もる）＋0.5 秒までは、マイク入力を捨てる
- 話し始めの区切りの音量（20ms ごとの RMS の最大値）が -35 dBFS 未満なら発話とみなさない

応答の再生中に話しかけても受け付けない（割り込みは非対応）。代わりに、話し終えてから応答が始まるまでが約 0.3 秒延びる。

## ツールの扱い方（2 方式）

| 方式 | 判定・呼び出し | 結果の返し方 |
|---|---|---|
| **2 段階**（既定） | 判定パス: 既定の指示なし＋ツール一覧の system と、今回の発話だけを入力する。先頭トークンが `<|tool_call_start|>` になる確率がしきい値以上ならツールコールを生成させる | 応答パス: 既定の指示あり・ツール一覧なしの system に全履歴を入れ、結果を `user` のテキストターン（`ツールの実行結果: ...`）として渡して音声で答えさせる |
| **ネイティブ** | 公式テンプレート通りに system にツール一覧を入れ、通常の生成中に出たツールコールを拾う | 公式テンプレート通りの `tool` ターン |

どちらの方式でも、ツールコールの区間（`<|tool_call_start|>`〜`<|tool_call_end|>`）は音声を挟まずテキストだけで生成させる。interleaved 生成は「テキスト 6 トークン → 音声 9 フレーム」を強制的に交互に出すので、そのままだとツールコールの途中に音声が割り込み、構文が壊れるため。

## 検証結果（Apple M3 / 16GB、MPS、bf16、2026-10-24 時点）

入力音声は macOS の `say -v Kyoko` で合成したもの。

### システムプロンプト

- 既定の指示 `Respond with interleaved text and audio.` は**必須**。外すと応答に中国語が混ざったり、同じ語を繰り返したりして崩れる。カスタム指示はこの一文の前後どちらに置いても問題なかった
- 長いシステムプロンプトにはかなり弱い:

| system の長さ | 最初のトークンまで | 生成速度 | 名簿を参照した回答 |
|---|---|---|---|
| 約 1k tokens | 約 1 秒 | 12〜15 step/s | テキストで質問すると 3 問中 1 問正解。音声で質問すると部署のみ当たる程度 |
| 約 2k tokens | 約 2 秒 | 11〜14 step/s | ほぼ誤答。崩れも出始める |
| 約 4k tokens | 約 3.5 秒 | 8〜15 step/s | 誤答。崩れが目立つ |
| 約 8k tokens | 約 7 秒 | 2〜7 step/s | 文章が崩れる |
| 16k / 30k tokens | — | — | 動作はする（OOM なし）が出力は崩れる |

- 長文での崩れは MPS の計算誤差ではない。同じ入力を CPU fp32 で実行しても生成テキストが完全一致した
- 会話のたびにコンテキスト全体を prefill し直すため、システムプロンプトが長いほど毎ターンの応答開始が遅くなる

### ツールコール

- **ネイティブ方式**: 既定の指示があるとツールを呼ばない（「天気は提供できません」と断る、時刻を捏造する）。既定の指示を外すと `get_weather(city="Tokyo")` のような正しいツールコールを出すが、応答文が崩れる。さらに `tool` ターンの後の応答も崩れる
- **2 段階方式**: 単発の質問 14 問（ツールを呼ぶべき 8 問・呼ばなくてよい 6 問）で、呼ぶかどうかの判断は全問正解した。複数ターンの会話（8 ターン）でも全問正解。ツールの結果を使った応答も崩れない
  - 判定時の確率は、呼ぶべき質問で 0.0076〜0.66、呼ばなくてよい質問で 0.0026 以下だった。既定のしきい値 0.005 はこの間に置いている
  - 確率ではなく先頭トークンの argmax で判定すると、8 問中 2 問しか呼ばなかった
- 既知の制限:
  - 引数の取り出しが不正確。「123かける456」が `123456 * 0.96` に、「札幌」が `Tokyo` に、「2980円」が `1980` になった（数値や固有名詞の聞き取り）
  - 判定パスには今回の発話しか入れないので、「じゃあ大阪は？」のように前の発話を参照する依頼は正しいツールを選べない。履歴を入れると、2 ターン目以降はほぼ呼ばなくなる
  - 判定パスのぶん、1 ターンあたり 0.15〜0.7 秒ほど応答開始が遅れる（高速化後。高速化前は 0.5〜1.5 秒）
- 実際のマイク音声での追加検証（2026-10-25）: 合成音声 19 問と実録音 8 件で、ツールの説明の書き方を比べた
  - 現行の説明（例: `現在の日付と時刻を取得する`）では 22/27 問。実録音の「明日の天気教えて」で、天気ではなく `get_current_time` を選んだ
  - 「いつ使うか」を説明に書く（例: `今の時刻や今日の日付を聞かれたときだけ使う`）と 23/27 問。「明日の天気」が `get_weather` になり、悪化した問いはなかった。サンプルのツール定義はこちらにしている
  - 説明に加えて `get_weather` に `date` 引数を足すと 22/27 問。割引計算を呼ばなくなった
  - どの書き方でも「1たす1は？」は正しく呼べない。合成音声では `set_timer(label='1+1', minutes=1)`、実録音では「一足一は」と聞き取って `get_current_time` になる。数の聞き取りと計算の依頼は、このモデルの苦手分野
- 呼ばなくてよい質問での誤検出（合成音声 15 問）:
  - 「日本の首都は？」（p=0.12）、「もう一回言って」（0.078）、「こんにちは」（0.043）、「おはよう」（0.035）で `get_current_time` を呼んだ
  - 「二番目に高い山は？」（0.0053）が `get_weather(city='Mount Everest')`、「答えは？」（0.0055）が `get_weather` になった
  - 呼ぶべき質問の確率は 0.006〜0.78 で、呼ばなくてよい質問の確率と大きく重なる。しきい値をどこに置いても分けきれない。迷うと `get_current_time` に倒れるのはモデルの癖

### 前の返答の繰り返し

このモデルは会話履歴があると、自由回答の依頼に**直前の返答をそのまま返す**ことが多い。ノイズのない合成音声で、高速化をすべて切っても再現する（モデル自体の挙動）。

| 会話 | 結果 |
|---|---|
| 「自己紹介して」→「何か面白い話をして」→「なぞなぞを出して」→「答えは？」 | 2 ターン目以降すべて自己紹介をそのまま繰り返す |
| 「東京の天気を教えて」（ツール）→「何か面白い話をして」 | 天気の答えをそのまま繰り返す |
| 「日本で一番高い山は？」→「何か面白い話をして」 | 富士山の話を続ける（作り話を含む） |

- 同じ質問を会話の最初に聞くと正しく答える（物語を話す、なぞなぞを出す）。「日本で一番高い山は？」のような答えのはっきりした質問は、履歴があっても正しく答える
- system プロンプトの有無、text temperature（0 / 0.7）、ツール結果の渡し方（別の user ターン / 同じ user ターン / tool ターン）を変えても直らない。過去の返答をテキストだけにすると悪化した
- 履歴を入れなければ繰り返さないが、「答えは？」「二番目に高い山は？」のような前の発話を受けた質問に答えられなくなる
- 自由回答の依頼では、自己紹介が「迷ったときの答え」になっている。合成音声の「何か面白い話をして」は、そのままなら物語を話すが、前後に 0.8 秒の無音を足すだけで自己紹介になる。WebRTC 経由の録音でも自己紹介になった（無音を削っても、16kHz に変換しても同じ）

対策として、**返答の書き出し（最初の音声より前に出るテキスト 6 トークン）が履歴中の返答と同じなら生成を打ち切り、履歴を捨てて system ＋今回の発話だけで答え直す**ようにした（画面の「生成パラメータ」でオン/オフ。既定はオン）。

- 繰り返した部分は音声になる前に打ち切るので、再生されない。答え直したターンは会話ログに「🔁 答え直し」と出て、統計表の備考に破棄した時間が出る
- 答え直すと、会話はそのターンからやり直しになる（それより前の履歴は使わない）
- 答え直したターンは、応答開始が 0.4〜1 秒ほど遅れる
- 効果（合成音声の会話）: 天気・自己紹介の後の「何か面白い話をして」が物語になった。WebRTC 経由の録音では、天気の繰り返しが自己紹介に変わっただけで、正しい答えにはならなかった
- 富士山の話を続けるケースは、書き出しが違うので検知しない

### 速度

高速化後の目安（MacBook Air M3、MPS）:

- 応答の最初のトークンまで: 0.1〜0.15 秒
- ツール判定: 0.15〜0.7 秒
- 生成速度: 約 32 step/s
- RTF（生成時間 ÷ 音声の長さ）: 約 0.5。リアルタイムの約 2 倍の速さ

長い system プロンプトでも、2 ターン目以降は KV キャッシュを使い回すので応答開始は 1 秒前後。

計測方法、ボトルネックの分析、各最適化の効果は [docs/performance.md](docs/performance.md) にまとめた。高速化は環境変数 `LFM_OPTS` で個別にオン/オフできる（`all` が既定、`none` で無効）。

## CLI（マイクなしで検証）

macOS の `say` で合成した音声をユーザー発話として入力できる。応答音声は `outputs/turnN.wav` に保存される。

```bash
uv run python cli.py --say "大阪の天気はどう？" --say "傘はいるかな"
uv run python cli.py --no-tools --filler-tokens 2000 --say "木村さくらさんの部署と内線番号を教えて"
uv run python cli.py --tool-mode native --base none --say "今何時？"
uv run python cli.py --system-prompt-file my_prompt.txt --say "こんにちは"
```

## ファイル構成

| ファイル | 内容 |
|---|---|
| `app.py` | Gradio 画面（付属デモを拡張したもの） |
| `engine.py` | モデル読み込み、system ターンの組み立て、ツール判定、ツールループ付きの interleaved 生成 |
| `tools.py` | サンプルツールの定義、モック実装、ツールコールのパース（Pythonic / JSON） |

| `cli.py` | CLI |

| `bench/` | 速度計測スクリプト・固定入力音声・計測結果 |
